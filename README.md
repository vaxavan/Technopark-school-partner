# Система управления публикациями и мониторинга партнёрской сети

Информационная система технопарка. Она принимает информационные поводы от авторов, готовит с помощью YandexGPT тексты
под ВКонтакте, Telegram, Max, Дзен и сайты школ, проводит их через утверждение и публикует по расписанию. Затем рассылает материал
школам-партнёрам, сама находит его на их сайтах и строит отчёт с доказательствами.

Архитектура соответствует отчёту по практике: модульный монолит с портами и адаптерами,
Django + Django REST framework, Celery + Redis, PostgreSQL, Playwright, Docker Compose.
Интерфейс пока на шаблонах Django. Всё, что он умеет, доступно и через REST API, поэтому отдельный фронтенд
(React) подключается без изменений сервера — план в [docs/ФРОНТЕНД.md](docs/ФРОНТЕНД.md).

## Быстрый запуск (Windows, macOS, Linux)

Нужен **Docker Desktop** (docker.com/products/docker-desktop). Установите его и запустите.

```bash
git clone https://github.com/vaxavan/Technopark-school-partner.git
cd Technopark-school-partner
copy .env.example .env        # Windows (PowerShell/cmd)
# cp .env.example .env        # macOS / Linux
```

Откройте `.env` в любом редакторе и заполните минимум:

| Переменная | Что вписать |
|---|---|
| `DJANGO_SECRET_KEY` | любая длинная случайная строка |
| `DIRECTOR_PASSWORD`, `ADMIN_PASSWORD` | пароли для входа |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | из `legacy/TechnoparkTest/.env` (рабочий прототип) |

Остальное можно оставить пустым: эти сервисы будут работать в демо-режиме (см. [docs/ТОКЕНЫ.md](docs/ТОКЕНЫ.md)).

```bash
docker compose up -d --build
```

Первая сборка занимает 5–10 минут: скачивается браузер для снимков страниц. Когда сборка закончится:

- **http://localhost:8000/f/istok/** — публичная форма заявки (ссылку получают авторы);
- **http://localhost:8000/login/** — рабочее место (e-mail и пароли директора и администратора из `.env`; если e-mail не задан — `director@istok.local` / `admin@istok.local`);
- **http://localhost:8000/api/docs/** — описание REST API;
- **http://localhost:8000/django-admin/** — служебная админка.

При первом запуске сами создаются организация, директор, администратор и справочник из 18 школ
(`data/schools.xlsx`).

Полезные команды:

```bash
docker compose logs -f worker                                     # что делают фоновые задачи
docker compose exec web python manage.py check_integrations       # проверить ключи и доступ к сайтам школ
docker compose exec web python manage.py crawl_schools            # обойти сайты школ прямо сейчас
docker compose down                                               # остановить (данные сохраняются)
```

## Развёртывание на сервере

Для сервера с доменом и HTTPS есть `docker-compose.prod.yml` (автоматический сертификат через Caddy, ежедневные
резервные копии базы) и скрипт `prod.sh`. Пошагово для Beget: [docs/ДЕПЛОЙ_BEGET.md](docs/ДЕПЛОЙ_BEGET.md).

Если сайты школ не открываются с сервера (не пускают адреса хостинга), их проверяет агент обхода на
компьютере, где они открываются, или обход идёт через прокси: [docs/АГЕНТ_ОБХОДА.md](docs/АГЕНТ_ОБХОДА.md).

## Как работает процесс

1. **Заявка.** Автор заполняет форму без регистрации и прикладывает фото. Пока YandexGPT проверяет полноту
   сведений, автор видит экран ожидания с анимацией и подсказками; затем — не больше двух раундов уточняющих
   вопросов (текст, «да/нет» или варианты; их можно пропустить). Если модель не ответила вовремя, вопросы
   пропускаются. Повторная отправка формы (двойной щелчок, «Назад») не создаёт вторую заявку. Если автор закрыл
   страницу с вопросами, через полчаса заявка всё равно уходит в редакцию. Автор и администратор получают письма.
2. **Решение.** Администратор принимает заявку (выбирает площадки), отклоняет с причиной или запрашивает материалы.
   В последнем случае автор получает ссылку, чтобы дополнить заявку.
3. **Тексты.** В фоне модель готовит вариант под каждую площадку. Каждый вариант проверяется: длина под площадку,
   числа, даты и имена, которых не было в заявке. При замечаниях модель переписывает текст, максимум 3 попытки.
   Если модель недоступна, создаются черновики из заявки, и администратор правит их вручную.
4. **Правка.** Исходный текст автора всегда виден рядом. Править можно вручную или командами модели
   («сократить», «официальнее», своя команда). Все версии сохраняются, для каждой считается доля ручных правок и правок моделью.
5. **Утверждение.** Директор утверждает сам. Администратор утверждает с отметкой «устно согласовано с директором»
   или «без согласования», и директор получает письмо. Отметку «утвердил директор» ставит только директор.
6. **Публикация** выходит в назначенное время: ВКонтакте, Telegram, Max, Дзен (через RSS-ленту `/rss/istok.xml`).
   Повторной публикации не бывает: если воркер упал посередине, запись уходит в «проверить вручную».
   Для каждой публикации сохраняется доказательство: адрес, время, снимок экрана, копия страницы и SHA-256.
7. **Школы.** После публикации материал рассылается активным школам, по отдельному письму каждой, со ссылкой
   «отметить размещение» и ссылкой на отписку. Каждый день система обходит ресурсы школ: карта сайта → RSS →
   ВКонтакте → раздел сайта. Тексты сравниваются цепочками по 4 слова (Жаккар и доля вхождения). Итог:
   **≥ 0,60** — подтверждено (со снимком), **0,35–0,60** — требует решения администратора, ниже — не найдено.
   Через 3 и 6 дней школа получает не больше двух напоминаний.
8. **Отчёт** по каждой паре «материал — школа» с выгрузкой в Excel и архивом снимков (ZIP).
9. **Поиск по сайтам школ.** Любая тема («битва роботов»), а не только наш текст: система обходит сайты
   выбранных школ в фоне, находит публикации с этой фразой в любой форме, сохраняет снимки и выдаёт
   Excel «есть / нет» и архив с папкой на каждую школу. Подробно — [docs/ШКОЛЫ_И_ПОИСК.md](docs/ШКОЛЫ_И_ПОИСК.md).

Фото, снимки и копии страниц лежат в томе `media`, в базе — только пути к ним:
[docs/ХРАНЕНИЕ_ФАЙЛОВ.md](docs/ХРАНЕНИЕ_ФАЙЛОВ.md).

## Устройство кода

```
src/
  config/          настройки, Celery, маршруты
  accounts/        организации, членство и роли (один пользователь — несколько организаций)
  core/            журнал событий (он же очередь уведомлений), порты, шифрование токенов
  integrations/    адаптеры: YandexGPT, почта, снимки страниц (Playwright)
  submissions/     заявки, уточняющие вопросы (JSON-схема + pydantic)
  materials/       материалы, конечный автомат (domain.py), подготовка и проверка текстов, утверждение
  publishing/      площадки (VK, Telegram, Max, демо), расписание без повторов, доказательства, RSS
  partners/        модуль контроля школ — порты и адаптеры, как на схеме 5:
    domain/          сущности и сравнение текстов, чистый Python без Django
    application/     порты и сценарии DispatchToPartners, DetectPlacement, RemindPartner, ResolveDisputedPlacement
    infrastructure/  модели Django, репозитории, обходчики сайтов, почта
    interfaces/      задачи планировщика, импорт Excel, отчёт
    container.py     сборка зависимостей
  web/             интерфейс на шаблонах и REST API
tests/             автотесты (pytest)
legacy/            первый прототип (генерация и мониторинг), из него перенесена логика
```

## Тесты

```bash
pip install -r requirements.txt
pytest                      # на SQLite, ~10 секунд
```

Чтобы прогнать тесты на PostgreSQL, задайте `TEST_WITH_POSTGRES=1` и переменные `POSTGRES_*`.

## Запуск без Docker (для разработки)

```bash
pip install -r requirements.txt
cd src
python manage.py migrate
python manage.py init_system
python manage.py runserver
```

Без `REDIS_URL` фоновые задачи выполняются сразу в процессе веб-сервера, а база — SQLite.
Чтобы материалы выходили по расписанию, во втором окне терминала запустите `python manage.py scheduler`.
